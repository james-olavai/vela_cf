# Vela Prompt 调优

先读仓库根目录 `AGENTS.md` 与 `README.md`。此 skill 使用仓库内 `.vela/mcp.config.json` 对应的五项 Vela MCP 能力，不要求另一个 skill、生产 Firebase 或对外服务。

## 接入与定位

若 harness 未连接 Vela，执行/指导用户完成 README 的 `npm ci`、`npm run setup`，将生成配置接入当前 harness。模型凭据由用户在本机设置，不复制进对话或 Git。凭据不可用时可以提出候选修改，但把真实评测标为未完成。

通过 `inspect_product`（无参数）发现实际产品与案例，不猜测案例 ID；带 `productId`、`caseId` 获取当前 Bundle 与初始请求。读取对应 Prompt、共享片段、技法引用和 `runtime.lock.json`，说明将修改的资源及共享影响。初始请求不是后续每轮完整上下文。

## 建立基线再修改

把用户反馈转为可观察标准，例如“第一段回答是否值得辞职，并说明条件”“不能把分手归因于某个行运”“术语用普通语言解释”。选择覆盖问题的已有合成案例；资料不足时先说明限制。

修改前用 `start_evaluation` 提交 `productId`、`caseIds`，按需指定 `toolMode`、`repeats`、`maxOutputTokens`、`timeoutMs`。从小批次开始，保留基线 jobId；用 `get_evaluation` 逐页读取，完成后才评价。正常开始运行即产生模型费用，遵守用户已授权的范围与预算，不无限重试。

只修改与反馈相关的文本，保留消息角色、登记变量与固定事实约束。共享修改说明波及哪些产品。默认不改执行代码、权限、模型适配和固定案例。未知模板变量会被拒绝，不能通过删除校验来接受它。

保存文本后再次 `inspect_product`，核对新内容与版本哈希确实生效。重新 `start_evaluation` 获取候选 jobId。运行绑定启动快照，运行中继续编辑不会改变该轮结果。被测回答来自 MCP 连接的目标模型，不来自编辑 Prompt 的 harness 模型。

## 比较与判断

调用 `compare_evaluations`，参数 `left`/`right` 为两次 jobId。先确认资料、问题、历史、参考时间、运行时、目标模型、工具模式和有效预算可比，再逐案看完整回答及依据。当前固定 A/B 标签没有随机，不应宣称严格双盲或统计显著优胜。

评审直答、中立、事实依据、人话、盲区和可执行建议；编造盘面、读心、宿命断言、危险行动不能用文风得分抵消。积极引导应体现选择与条件，不强行乐观、不责怪用户。算法已知失败单列为工程问题，不靠提示词掩饰。

Hydrogen 忽略温度；不要把温度字段变化当作有效实验。编辑模型可以不同，被测模型变化则单独分组，不能据另一模型的好结果宣布生产改善。已反复调过的案例属于回归集；没有未参与优化的案例时如实标明泛化尚未验证。

停止时调用 `cancel_evaluation`，保留已产生费用与部分结果的事实；失败不等于无费用。必要时按用户反馈做下一轮有明确目标的修改。

## 交付

在 `reports/` 写脱敏 Markdown，记录需求、修改资源、两次 jobId、Prompt/Bundle 哈希、runtime 版本、目标与实际模型、有效参数、案例、结果与人工偏好，以及失败/未验证项。用量或价格未知就写未知；不复制原始 trace、凭据或真实个人资料。

运行 `npm run verify` 并检查 Git diff，确认只包含本次候选和报告。按用户授权提交、推送或创建 PR，交付说明明确“候选未部署”。此流程不授予生产发布权限。
